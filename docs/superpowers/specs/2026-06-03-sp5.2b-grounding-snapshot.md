## Findings Summary

### (a) CLI token form for negative limit
- **WORKING:** `--limit-price=-50.00` (equals sign, no space between flag and value)
- Alternate form `--limit-price -50.00` (space) was NOT tested (ordered clean; not needed; document for future reference: Go flag parsing sometimes interprets the negative number as a separate positional)
- The API echoes `"limit_price": "-50"` — sign round-trips intact

### (b) Signed semantics confirmed live
- A credit-demand of −$50 rests unfilled on a spread with fair credit ~$1.06
- SP-5.0's historical mistake (+50 on a credit spread = "pay ≤ $50 per share" = immediately marketable) is inverted: −50 = "receive ≥ $50" → far OTM demand → rests
- The semantic axis is: more positive = more willing to pay = more marketable; more negative = demanding more credit = less marketable

### (c) Iron condor acceptance
- 4-leg mleg order accepted by Alpaca API without errors
- All 4 legs get individual leg IDs and rest independently
- Negative limit preserved across all legs
- This is the first live 4-leg iron condor submission in this system — construction validated

### Surprises / Edge Cases
- None. The probe proceeded exactly as anticipated.
- The `{}` cancel response is normal Alpaca behavior (empty body on success).
- Open orders list showed 6 pre-existing equity OCO/stop orders — not probe-related.

## Implications for SP-5.2b Implementation

1. The implementation must use `--limit-price=-{abs_credit:.2f}` (equals form) when submitting credit structures via CLI
2. Net credit calculation: `short_leg_bid - long_leg_ask` (for a spread); sum across sides for condor
3. Limit price sign convention: credit received → negative float → demand parameter; debit paid → positive float → maximum willingness to pay
4. The mleg endpoint is fully capable of 4-leg structures without special treatment
5. The API echoes the limit_price as a string; parse with `float(response['limit_price'])` — will be negative for credit orders
