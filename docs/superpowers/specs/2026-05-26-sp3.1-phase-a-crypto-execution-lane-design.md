# SP-3.1 Phase A — Crypto Execution Lane (Design)

**Date:** 2026-05-26
**Status:** Design — approved, pending spec review
**Program:** SP-3.1 (Crypto + 24/7), Phase A of A→D
**Predecessor:** SP-3 Asset-Class Expansion MVP (merged `c2f72ca`; `instrument_class` enum with `crypto` reserved-but-unhandled)

---

## 1. Goal

A crypto order can route to the Alpaca broker and **fill**, on the existing daily cycle, without disturbing the equity path. Executor + sizer only.

**Explicitly NOT in Phase A:** crypto market-data wiring (→ Phase B), a crypto regime detector (→ Phase B), 24/7 monitoring / overnight redeploys (→ Phase C), a reference crypto strategy (→ Phase D).

## 2. Background & motivation

SP-3 shipped a strategy-level `instrument_class` enum. `equity`/`option`/`etp` are routed; `crypto`/`futures` are **valid-but-unhandled** — the sizing dispatcher raises `NotImplementedError` for them (`src/execution/instrument_class_sizer.py:37-41`). SP-3.1 adds the crypto handler. Crypto's defining property — 24/7 trading — breaks invariants baked into the equity execution path; Phase A handles the *execution* half (order shape), deferring the *session/regime* half to Phases B–C.

Two hard constraints discovered during grounding drive the design:

1. **The CLI cannot use notional orders for crypto.** `alpaca order submit --notional` is documented "Can only work for market order types and **day** for time in force." Crypto orders cannot use `day` TIF, so crypto must submit **fractional `--qty`** (the `--qty` flag is a string and accepts e.g. `0.0166`). This also sidesteps the equity path's `qty = max(1, int(notional / entry))` (alpaca_executor.py:958), which would floor a $1k order on $60k BTC to a single ~$60k unit.

2. **The equity order path gates on market session.** `_alpaca_session_kind()` (alpaca_executor.py:144) returns `rth|premarket|afterhours|closed` and refuses `closed`; `_skip_extended_hours` (`:667`) rejects any asset whose Alpaca `class != us_equity`. Crypto is always open and is class `crypto`, so it must bypass both — it cannot ride the equity session rails.

## 3. Architecture — single upstream intercept

Crypto is detected and handled **before** the equity session/qty logic. Everything non-crypto falls through unchanged, preserving the SP-3 "equity byte-identical" invariant.

### 3.1 The routing helper

```
_route_crypto_order(order, coid) -> dict | None
```

- Returns a **result dict** (same shape the equity path returns: `status`, `qty`, `notional`, `entry`, `order_id`, `tif`, `order_class`, `client_order_id`, …) when it handled a crypto ticker.
- Returns **`None`** to signal "not crypto — fall through to the equity path."
- Crypto detection: the ticker carries the `-USD` suffix convention (mirrors collector.js `_classifyMarketTicker`, which routes `/-USD$/ → crypto`). The helper checks this suffix; non-matching tickers return `None` immediately, so the equity path is never altered.

### 3.2 Two call sites (both mandatory)

The helper is invoked at **both** interception points. Missing either ships a "crypto can open but cannot close overnight" bug that would not surface until Phase C.

1. **`close_only` branch** — `src/execution/alpaca_executor.py:847` (just inside `if order.get('close_only'):`, before `session_co = _alpaca_session_kind()` at `:848`).
2. **Main entry branch** — `src/execution/alpaca_executor.py:957` (immediately before `notional = equity * pct_nav` / `qty = max(1, int(notional/entry))` / `session = _alpaca_session_kind()`).

In both sites: `res = _route_crypto_order(order, coid); if res is not None: return res`. A non-crypto ticker yields `None` and the existing code runs verbatim.

## 4. The crypto order path (inside the helper)

### 4.1 Symbol mapping

`BTC-USD → BTC/USD`. Python port of `src/pipeline/collector.js:638` (`_alpacaCryptoSymbol`): replace `-` with `/`. Lives as a small module-level helper so it is unit-testable.

### 4.2 Fractional-qty sizing (open / entry)

1. Fetch the live crypto price via `alpaca data crypto latest-trades --symbols BTC/USD` (CLI surface confirmed present). Parse the latest trade price.
2. `qty = notional_usd / price`, rounded to the precision Task 0 establishes Alpaca accepts (decimal places + minimum order size).
3. Submit `alpaca order submit --symbol BTC/USD --qty <fractional> --side <buy|sell> --type market --time-in-force <TIF from Task 0>`.
4. **No bracket, no `--extended-hours`, no `_alpaca_session_kind` gate.** Crypto is always open.
5. **No broker-side stop/target in Phase A.** Crypto does not support brackets; we submit entry-only. Crypto stop-management is a documented Phase D fast-follow tied to the reference strategy. (Candidate-only discipline — nothing live trades crypto yet, so there is no unmanaged-risk exposure in Phase A.)
6. Price-fetch failure or non-positive price → return a `SKIP` result (same shape as the equity "no quote" skips), never a raw exception.

### 4.3 Close path (`close_only`)

`alpaca position close --symbol-or-asset-id BTC/USD`, with `--percentage <pct>` for a partial reduce (same partial-reduce math the equity close path uses at alpaca_executor.py:863-870). No "market closed" refusal — crypto is always open. (Whether the CLI accepts crypto symbols for `position close` is confirmed in Task 0.)

### 4.4 Audit-record shape

The returned dict must populate the same non-null fields the reconciler expects (`order_id`, `qty`, `notional`, `entry`, `tif`, `order_class='simple'`, `client_order_id`) so `record_submission` (alpaca_executor.py:340) and reconcile write a complete row. `entry` for crypto = the fetched latest-trade price used for the qty conversion.

## 5. Sizer handler

`src/execution/instrument_class_sizer.py`:
- Remove `crypto` from `_RESERVED` (leaving `_RESERVED = {"futures"}`).
- Add a `crypto` pass-through branch (mirrors `equity`/`etp`: return the order unmodified — notional sizing, no greeks). Vol-scaled crypto sizing is deferred (later SP-3.x).
- `futures` continues to raise `NotImplementedError`.

This handler runs only when `OPENCLAW_INSTRUMENT_CLASS_ROUTING=1` (the dispatch at `regime_blended_sizer_live.py:127-134`). When OFF, no order is ever tagged crypto, the sizer never special-cases it, and the executor helper is never reached.

## 6. Task 0 — grounding spike (mandatory, blocks all plan tasks)

Fire **real $5 paper orders** against the live Alpaca paper account and write the actual CLI responses to a snapshot file (`docs/superpowers/specs/sp3.1-task0-crypto-cli-snapshot.md` or similar). Subsequent plan tasks cite this file with exact response shapes — this is the discipline that prevents the SP-2 plan-schema-drift failure (plans referencing names/shapes that don't exist). The spike must produce evidence for:

1. **TIF** — the exact `--time-in-force` value `alpaca order submit --symbol BTC/USD --qty 0.001 --side buy --type market` accepts (`gtc` / `ioc` / possibly `day`). Record the accepted value and any rejection messages for the others.
2. **Fractional-qty precision** — how many decimal places Alpaca accepts on `--qty`, and the minimum order size / minimum notional it enforces (record the rejection if `0.0001` is too small).
3. **Close path** — whether `alpaca position close --symbol-or-asset-id BTC/USD --percentage 50` accepts crypto symbols, and the response shape (`id`/`order_id`/`qty`).
4. **Response shape** — capture the full JSON of a successful crypto `order submit` so the audit-record mapping (§4.4) is grounded, not guessed.

These are low-risk (paper account, small notional) but must be **observed, not inferred from memory or docs**.

> **Post-execution correction (Task 0 finding):** Alpaca's crypto **minimum order is $10 cost basis**, not $5. Wherever this spec says "$5" the live smoke used **$20** (≥ minimum). See `sp3.1-task0-crypto-cli-snapshot.md` for the authoritative captured values (`gtc` TIF, $10 min, `id` order-key, 9-dp qty).

## 7. Scope boundary & exit criterion

**Phase A is done when:**
- Unit tests pass on `_route_crypto_order` and the symbol-map helper using fixtures (crypto-suffix detection, fractional-qty math, skip-on-no-price, close-path arg construction, non-crypto → `None` fall-through).
- A gate-parity test confirms the equity path is byte-identical with the helper present (non-crypto orders return `None` and run the existing code).
- **One live $5 paper BTC order submitted, confirmed filled, and confirmed recorded correctly by reconcile.**

**Deliberately deferred (NOT Phase A):**
- Crypto bars in `prices.parquet` and any `universe_config` change. `universe_config` is shared config — adding crypto rows changes what every consumer (collector, resolver, options/news backfills) sees. Phase A needs no bars (executor is fixture- + single-live-order-tested), so it does **not** touch `universe_config`. Data wiring → **Phase B**.
- A `OPENCLAW_CRYPTO_ENABLED` sub-gate — unnecessary in Phase A (no strategy to gate). Added when **Phase D** mints the reference strategy.
- Broker-side crypto stops → **Phase D**.

## 8. Testing strategy

- **Unit (fixtures):** symbol map; crypto-suffix detection; fractional-qty computation at a known price; SKIP on price-fetch failure; close-path `--percentage` math; **non-crypto ticker returns `None`** (the byte-identical guard).
- **Gate parity:** with the helper wired into both call sites, an equity order produces the identical result dict it produced before (the SP-3 parity-test pattern).
- **Live smoke (Task 0 + final):** one $5 paper BTC buy → fill → reconcile row; one partial close → reconcile row.

## 9. Risks & mitigations

| Risk | Mitigation |
|---|---|
| CLI TIF/precision differs from assumption | Task 0 spike produces real evidence before any code task |
| Helper added to only one call site (open-but-can't-close bug) | Spec mandates both `:847` and `:957`; a close-path unit test enforces it |
| Equity path regression | `None`-fall-through design + gate-parity test + equity orders never enter the helper |
| Unmanaged crypto risk (no broker stop) | Phase A is candidate-only — no live crypto strategy exists; documented Phase D fast-follow |
| `universe_config` shared-state contamination | Phase A does not touch it (data wiring deferred to Phase B) |

## 11. Phases B–D (preview, not specced here)

- **Phase B — Crypto regime detector + data wiring:** new HMM on crypto features, own backfill + persisted table (append-only-safe), 24/7 tick at cadence = f(bar timeframe), default hourly; wires crypto bars into collection (`universe_config` decision lands here).
- **Phase C — 24/7 monitoring + instrument-class-scoped redeploy:** crypto regime-transition → crypto-only redeploy (equity stays RTH-gated, untouched overnight); redeploy ship-gate + doctor freshness become class-aware.
- **Phase D — Reference strategy + thresholds:** crypto entries in `INSTRUMENT_COST_BPS` + `PROMOTION_THRESHOLDS`; mint one reference crypto strategy (candidate-only); broker-side crypto stops; `OPENCLAW_CRYPTO_ENABLED` sub-gate.
