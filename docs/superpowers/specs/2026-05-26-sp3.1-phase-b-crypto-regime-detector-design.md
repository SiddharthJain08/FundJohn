# SP-3.1 Phase B — Crypto Regime Detector + Data Feed (Design)

**Date:** 2026-05-26
**Status:** Design — approved, pending spec review
**Program:** SP-3.1 (Crypto + 24/7), Phase B of A→D
**Stacked on:** Phase A crypto execution lane (branch `worktree-sp3.1-phase-a`)

---

## 1. Goal

Produce a fresh, crypto-specific market-regime signal **24/7**, persisted and isolated from the equity regime. Phase B only **produces** the signal; **consuming** it (firing redeploys, gating crypto strategies) is Phase C. The whole subsystem is behind a default-OFF gate so it is inert until enabled.

**Explicitly NOT in Phase B:** redeploy spawning, crypto-strategy regime gating, a reference crypto strategy, daily crypto bars in `prices.parquet` for strategy backtests (all Phase C/D).

## 2. Background & grounding

- The existing HMM stack is **fully equity-centric**: `scripts/run_market_state.py` (daily, 4-state Gaussian HMM, 6 VIX/SPX/HYG/LQD features, weekly Monday refit, model at `.agents/market-state/hmm_model_latest.pkl`) and `scripts/run_intraday_market_state.py` (5-min ticks 9:30–16 ET, hysteresis tiers, spawns `scripts/redeploy_pipeline.py` on confirmed transition). No crypto features anywhere. Vocabulary: `LOW_VOL / TRANSITIONING / HIGH_VOL / CRISIS` (ascending vol).
- The daily and intraday HMMs are **separate scripts, not a shared module** — so a parallel crypto script is the established pattern and the lower-risk choice on a live system (no refactor of live equity code).
- Regime is consumed file-primary from `regime_latest.json` (`src/execution/engine.py:load_regime`, fail-hard if >80h stale); strategy eligibility via `src/strategies/regime_gate.py:is_eligible(strategy_id, regime_state)` against `strategy_regime_params` (no row → eligible everywhere).
- **The price collector fetches `union_universe(live)`** (`src/pipeline/collector.js` reads Redis `universe:union:{date}:live`, falls back to the `universe_resolver` CLI), **not** `universe_config WHERE active`. No crypto strategy is live until Phase D, so crypto bars will not flow through the normal loop — the detector needs its **own** feed.
- Hourly `BTC/USD` bars are available via `alpaca data crypto bars --timeframe 1Hour` both recently and ≥2 years back (verified 2024-05-26); bar keys: `t,o,h,l,c,v,vw,n`. `prices.parquet` is daily EOD; the equity intraday HMM uses its own `data/master/intraday_features.parquet`.
- Highest existing migration is **117**; `intraday_regime_states` (migration 067) is the schema to mirror.

## 3. Architecture — a parallel crypto-regime subsystem (5 components)

### 3.1 Dedicated hourly crypto-bars feed
- `src/ingestion/crypto_bars.py` (new): fetch `BTC-USD`, `ETH-USD` 1H bars via the Alpaca CLI (`alpaca data crypto bars --symbols BTC/USD --timeframe 1Hour`, symbol mapped `-`→`/` reusing Phase A's convention), **independent of `union_universe`** — the symbol set is a small module constant `CRYPTO_REGIME_SYMBOLS = ('BTC-USD', 'ETH-USD')`.
- Writes to a **new append-only master parquet** `data/master/crypto_bars_1h.parquet` (NOT `prices.parquet`). Columns: `ticker, ts_utc, open, high, low, close, volume, vwap`. Keyed by `(ticker, ts_utc)`; append-only (new file starts empty; backfill is the initial write; hourly tick appends new rows). Added to the CLAUDE.md NEVER-DELETE master-data family.
- One-time backfill (~2y hourly, operator-invoked) to seed training history; an incremental fetch (last N hours) on each tick.

### 3.2 Crypto regime detector
- `scripts/run_crypto_market_state.py` (new), mirroring `run_market_state.py`: a 4-state Gaussian HMM (`hmmlearn`), **reusing the `LOW_VOL/TRANSITIONING/HIGH_VOL/CRISIS` vocabulary** (states ordered by ascending realized-vol mean, exactly as the equity HMM orders by ascending VIX mean), so Phase C/D reuse the existing `strategy_regime_params` / `active_in_regimes` gating.
- Model persisted to `.agents/crypto-market-state/hmm_crypto_latest.pkl` (+ dated snapshot), pickle, mirroring the equity convention. **Weekly refit** (Monday or model-missing), else load-and-predict.

### 3.3 Features — price-derived only (MVP)
Computed from the hourly bars in `crypto_bars_1h.parquet`. No external crypto IV index exists on Alpaca/FMP, so the feature set is backward-looking realized-vol based (honest limitation vs the VIX-anchored equity model; a crypto IV index is a future enhancement if a provider is added):
- `btc_rv_24h` — annualized realized vol of BTC hourly returns over a 24h window.
- `btc_rv_168h` — annualized realized vol over a 168h (7-day) window.
- `btc_vol_term_slope` — `btc_rv_24h / btc_rv_168h` (short/long realized-vol ratio; the crypto analogue of VIX term slope).
- `btc_ret_24h` — trailing 24h BTC return.
- `eth_btc_dispersion` — `eth_rv_24h - btc_rv_24h` (cross-asset stress/dispersion).

(Exact windows are the MVP defaults; the plan may tune them against the backfill. All derive from OHLCV — no new data source.)

### 3.4 Outputs + persistence
- `.agents/crypto-market-state/crypto_regime_latest.json` (+ dated archive), mirroring `regime_latest.json`'s shape (`date/ts_utc, state, state_probabilities, confidence, features, prior_state, days_in_state, refit_performed, ...`).
- New table **`crypto_regime_states`** (migration **118**), mirroring `intraday_regime_states` (067) with one rename — `fired_liquidation` → `fired_redeploy` (crypto fires redeploys, never liquidations; default FALSE in Phase B since B never fires):
  ```
  ts_utc TIMESTAMPTZ PRIMARY KEY, state TEXT NOT NULL, prior_state TEXT,
  confidence REAL NOT NULL, hysteresis_streak INTEGER NOT NULL DEFAULT 1,
  fired_redeploy BOOLEAN NOT NULL DEFAULT FALSE, transition_tag TEXT,
  features_json JSONB NOT NULL DEFAULT '{}', created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
  ```
  + a per-state ts-desc index (mirrors `idx_intraday_regime_state_ts`) for the hysteresis-lookback query.

### 3.5 Hysteresis + confirmed-transition (produced, not acted)
Mirrors the equity intraday hysteresis tiers (CRISIS fast/severe → LOW_VOL slow/conservative). On each tick the detector computes the raw state + confidence, applies hysteresis over the last-N `crypto_regime_states` rows, and when a transition is **confirmed** it writes the row with a `transition_tag` (e.g. `CRYPTO_HMM_{prior}_{new}`). **It does NOT spawn a redeploy** — `fired_redeploy` stays FALSE. The confirmed-transition signal is the hand-off contract Phase C consumes.

### 3.6 Hourly 24/7 tick
A new cron in `src/engine/cron-schedule.js` — `cron.schedule('0 * * * *', …)` (UTC, every hour, all days), spawning `scripts/run_crypto_market_state.py` detached (mirroring the intraday-HMM spawn at `cron-schedule.js:340-355`). Gated: the cron body early-returns unless `OPENCLAW_CRYPTO_REGIME=1` (default OFF).

## 4. Gate & isolation

- Default-OFF gate `OPENCLAW_CRYPTO_REGIME` (separate from Phase A's `OPENCLAW_INSTRUMENT_CLASS_ROUTING`). When OFF: the cron does nothing, the detector is never invoked, no new parquet/table writes occur in production. The migration (118) and code ship inert.
- The crypto regime is **fully isolated** from the equity regime: separate model, separate `crypto_regime_latest.json`, separate table. `engine.py`/`regime_gate.py` are **untouched** in Phase B (equity regime behavior byte-identical). Wiring crypto strategies to read the crypto regime is Phase C.

## 5. Scope boundary (B vs C vs D)

- **Phase B (this spec):** data feed + detector + persistence + confirmed-transition signal, gated OFF, isolated. Exit criterion: with the gate ON in a dev run, the backfill seeds `crypto_bars_1h.parquet`, the detector fits a model and writes a valid `crypto_regime_latest.json` + `crypto_regime_states` rows over a multi-tick run, and unit tests cover features/scoring/hysteresis/persistence.
- **Phase C:** consume the confirmed-transition signal → spawn an **instrument-class-scoped** crypto redeploy (crypto positions only; equity untouched); make `regime_gate`/redeploy ship-gate class-aware so crypto strategies gate on the crypto regime.
- **Phase D:** reference crypto strategy (candidate), daily crypto bars into `prices.parquet` for backtests, crypto `INSTRUMENT_COST_BPS`/`PROMOTION_THRESHOLDS`, `ROUTED_INSTRUMENT_CLASSES`+crypto, broker-side stops, and the **`alpaca_submissions.qty` `INT`→`NUMERIC` migration** (Phase A carry-forward: fractional crypto qty currently rounds to 0 in the audit row).

## 6. Testing strategy

- **Unit (fixtures):** feature computation on a synthetic hourly-bar frame (known RV/return values); HMM state-ordering (ascending RV → LOW_VOL…CRISIS); hysteresis streak/confirmed-transition logic on a synthetic state history; `crypto_regime_latest.json` shape; the symbol mapper reuse.
- **Data-feed:** `crypto_bars.py` parses the Alpaca bar shape (`t/o/h/l/c/v/vw`) and writes the parquet schema; append-only semantics (no row drop on re-run).
- **Integration smoke (gate ON, dev):** backfill a small window → fit → tick twice → assert a `crypto_regime_states` row + `crypto_regime_latest.json` exist and are well-formed. (No live trading — detector only reads market data.)
- **Equity non-regression:** the equity HMM scripts + `engine.py`/`regime_gate.py` are untouched; confirm by diff + the existing regime tests.

## 7. Risks & mitigations

| Risk | Mitigation |
|---|---|
| New master parquet violates append-only invariant | `crypto_bars_1h.parquet` is append-only; backfill is initial write, tick appends; added to CLAUDE.md NEVER-DELETE family; tests assert no row drop |
| Crypto regime model weak (no forward-looking IV) | Documented MVP limitation; price-derived RV features; IV index a future enhancement; gate OFF until validated |
| Accidental coupling to equity regime | Separate model/json/table; `engine.py`+`regime_gate.py` untouched in B (verified by diff) |
| Detector fires actions prematurely | B never spawns redeploys (`fired_redeploy` always FALSE); gate default OFF |
| Migration runner re-run wart (known) | Verify `crypto_regime_states` exists post-deploy (same check pattern as migration 117) |
