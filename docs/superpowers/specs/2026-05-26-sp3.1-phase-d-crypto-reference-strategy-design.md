# SP-3.1 Phase D — Reference Crypto Strategy + Activation (Design)

**Date:** 2026-05-26
**Status:** Design — approved, pending spec review
**Program:** SP-3.1 (Crypto + 24/7), Phase D of A→D — **the final phase; activates the whole crypto stack.**
**Builds on:** Phase A (crypto execution lane), Phase B (crypto regime detector), Phase C (crypto redeploy + per-strategy regime gating). All merged (`99ae99f`), all three gates default-OFF → currently INERT.

---

## 1. Goal

Mint the first live `instrument_class='crypto'` strategy (single-asset BTC momentum), wire the last enabling constants (cost model, promotion thresholds, routed-class membership), fix the `alpaca_submissions.qty` audit column so fractional crypto qty survives, add broker-side crypto stops (separate resting order — crypto has no bracket/OCO), then **promote the strategy live and flip all three gates** so crypto trades on the daily cycle and on crypto-regime transitions.

**Operator decision (this cycle):** unlike A/B/C (shipped inert), Phase D **activates**. Every live-affecting step (stops grounding spike, gate flips, promotion, restart, first-cycle smoke) is **surfaced for explicit operator OK before firing** — not fired autonomously.

## 2. Key de-risk — daily crypto bars are already present

The spec's "daily crypto bars into `prices.parquet`" deliverable is **already satisfied**. `data/master/prices.parquet` already carries 8 crypto tickers in long format — `BTC-USD` has **3,698 clean daily bars, 2016-04-10 → 2026-05-25 (fresh through yesterday), 0% null closes** — flowing automatically via SP-1's collector (`fillPricesAlpacaCrypto` → `_classifyMarketTicker` routes `-USD` → crypto). **Phase D builds NO backfill and touches NO `universe_config` row for this**; it only verifies the reference strategy's `min_lookback` (90d) is satisfied by the existing panel (it is, by ~40×).

## 3. Architecture (5 components + activation)

### 3.1 Constants — land FIRST (ordering is load-bearing)
`lifecycle.can_transition` reads `PROMOTION_THRESHOLDS[instrument_class]` and the backtest reads `INSTRUMENT_COST_BPS[instrument_class]`. If `crypto` is missing from either, the reference strategy cannot reach candidate or backtest cleanly. **These constants must land before the strategy registers.**

| Constant | File | Change |
|---|---|---|
| `INSTRUMENT_COST_BPS` | `src/backtest/unified_backtest.py:74` | add `"crypto": 25.0` (Alpaca crypto taker tier; record-only — no sim-math change, mirrors SP-3 cost model) |
| `PROMOTION_THRESHOLDS` | `src/strategies/lifecycle.py:97` | add `"crypto": {"min_sharpe": 0.5, "max_drawdown": 0.40}` + `TODO(SP-3.2) calibrate` |
| `ROUTED_INSTRUMENT_CLASSES` | `src/strategies/lifecycle.py:118` | add `"crypto"` (now `{equity, option, etp, crypto}`) |

**Crypto promotion thresholds rationale:** equity/etp use `max_drawdown ≤ 0.20`. A long-only BTC strategy cannot meet that — BTC has repeatedly drawn down >50%. Crypto's baseline volatility justifies a wider drawdown band; `0.40` is chosen **grounded by the actual reference-strategy backtest** (set to a value the risk-controlled strategy genuinely clears, not gamed below its observed MaxDD). `min_sharpe` stays at `0.5` (the bar for live alpha is class-independent). The sizer handler is unchanged — Phase A already moved crypto to pass-through in `instrument_class_sizer.py`.

### 3.2 Migration 119 — `alpaca_submissions.qty INT → NUMERIC`
`src/database/migrations/119_alpaca_submissions_qty_numeric.sql`: `ALTER TABLE alpaca_submissions ALTER COLUMN qty TYPE NUMERIC USING qty::numeric`. The executor already places the fractional qty in its result dict; `record_submission` (`alpaca_executor.py:340`) writes `alpaca_resp.get('qty')` into the column, which today is `INT NOT NULL` (migration 043) → fractional crypto qty truncates to 0 in the audit row. The migration is additive (widening type; no data loss; equity INT values cast losslessly). Applied to the live DB via psycopg2 (psql absent on VPS, as with migration 118). **Verified post-deploy** by `SELECT qty FROM alpaca_submissions WHERE ticker='BTC-USD' ORDER BY run_date DESC LIMIT 5` after the first crypto smoke — fractional qty must survive the round-trip.

### 3.3 Reference strategy `S_btc_momentum` (+ `.requirements.json`)
`src/strategies/implementations/S_btc_momentum.py` — mirrors `S_commodity_etp_momentum` structure but for spot crypto, with two risk controls so it is genuinely promotable:
- `id='S_btc_momentum'`, `instrument_class='crypto'`, `BASKET=('BTC-USD',)`, `min_lookback=90`, `signal_frequency='daily'`.
- **Signal:** 90-trading-day total-return momentum on BTC-USD.
- **Absolute-momentum gate:** if 90d return < 0, emit **no signal** (go to cash) — this is the primary drawdown control (avoids riding BTC bear markets).
- **Vol-targeting:** scale gross to a 20% annualized-vol target (`min(1, 0.20 / realized_vol)`), capped at a base gross fraction — mirrors the existing `S_btc_gold_dual_momentum_rotation` vol-target convention.
- `active_in_regimes` uses the crypto-regime state vocabulary (`LOW_VOL`/`TRANSITIONING`/`HIGH_VOL`/`CRISIS` — identical names to the equity HMM; Phase C's per-strategy gating routes this strategy's eligibility against `crypto_regime_latest.json`).
- Stops/targets via `compute_stops_and_targets` (ATR-based), as the ETP reference does. A `.requirements.json` sibling is written (the ETP reference lacking one is an outlier, not a pattern to copy).
- Lifecycle: registers as **candidate**, gets backtested, and — given activation — is **promoted to live** once it clears the crypto thresholds (§3.1).

### 3.4 Broker-side crypto stops (spike + ship)
Alpaca crypto supports no bracket/OCO; a stop must be a **separate resting order** placed after the entry fills — the correct design for a 24/7 asset the daily cycle cannot monitor overnight.
- **Task-0-style grounding spike** (mandatory, blocks the stop-implementation tasks): a real ~$15 paper BTC order, then submit a stop against the resulting position via the CLI to capture **which order type Alpaca crypto accepts** (`stop_limit` vs `stop`), the required params (stop price, limit price, TIF), and the response shape. Written to `docs/superpowers/specs/sp3.1-phase-d-crypto-stop-snapshot.md`. Where it differs from assumptions, the snapshot wins. **Surfaced for operator OK before the paper order fires.**
- **Implementation:** a helper `_submit_crypto_stop(api_symbol, stop_price, qty, coid)` invoked from `_route_crypto_order`'s open path after a successful entry, placing a resting stop at the signal's `stop_loss`. Fail-safe: a stop-submit failure logs + returns the entry result (never crashes the entry; the position is still software-managed by the next cycle). Gated by the same `OPENCLAW_INSTRUMENT_CLASS_ROUTING` path. The snapshot's captured type/params are used verbatim.

### 3.5 Activation (after build + two-stage reviews + smokes; each step OK-gated)
1. **Promote** `S_btc_momentum` candidate→live (must clear crypto `PROMOTION_THRESHOLDS`; if the backtest does not clear them, surface and stop — do not force-promote without operator sign-off).
2. **Flip** in production `.env`: `OPENCLAW_INSTRUMENT_CLASS_ROUTING=1`, `OPENCLAW_CRYPTO_REGIME=1` (crypto_bars_1h.parquet already seeded by Phase B's smoke — no first-tick crash), `OPENCLAW_CRYPTO_REDEPLOY=1`.
3. **Restart** johnbot; run the final live crypto smoke; monitor the first daily cycle / regime tick.

## 4. Safety invariants
- **Constants before strategy** — the strategy cannot reach candidate/live without crypto in `PROMOTION_THRESHOLDS`; cost model present before any crypto backtest.
- **Equity untouched** — Phase C's dedicated crypto redeploy + equity byte-identical engine path are unchanged; the daily sizer nets crypto into its existing target set (crypto position is in `target_usd`, never orphan-closed; equity positions in theirs).
- **Migration additive** — `INT→NUMERIC` widens; equity values cast losslessly; honors the NEVER-DELETE invariant (no column/row drop).
- **Stop fail-safe** — a stop-submit failure never aborts or unwinds the entry; the position remains software-managed by the daily/regime cycle.
- **Promotable on merit** — crypto thresholds are set to values the risk-controlled strategy genuinely clears in backtest, not lowered to force a marginal strategy live.
- **Live ops OK-gated** — spike paper order, gate flips, promotion, restart, first-cycle monitoring each require explicit operator OK.

## 6. Data flow
daily cycle `collect` (BTC-USD daily bars already in panel) → `S_btc_momentum.generate_signals` (90d momentum + abs-gate + vol-target, crypto-regime-gated via Phase C) → regime_blended_sizer_live → `instrument_class_sizer` (crypto pass-through, gate ON) → `_route_crypto_order` (fractional gtc market entry) → `_submit_crypto_stop` (resting stop at stop_loss) → `record_submission` (NUMERIC qty). Crypto-regime transition (Phase B tick, gate ON) → spawns Phase C `redeploy_crypto.py` (crypto-only, equity untouched).

## 7. Testing
- **Constants:** `INSTRUMENT_COST_BPS['crypto']`, `PROMOTION_THRESHOLDS['crypto']`, `crypto ∈ ROUTED_INSTRUMENT_CLASSES`; `_promotion_threshold('crypto')` returns the crypto row; `can_transition` for a crypto candidate uses crypto thresholds.
- **Migration round-trip:** insert a fractional qty (e.g. `0.00018`) into `alpaca_submissions`, read it back, assert it is NOT truncated to 0 (the load-bearing test for migration 119).
- **Strategy:** synthetic uptrend BTC panel → 1 LONG signal sized by vol-target; synthetic downtrend → empty (abs-momentum gate); insufficient history → empty.
- **Backtest:** `run_backtest(..., instrument_class='crypto')` runs with the crypto cost model; record the Sharpe/MaxDD that justify the threshold values.
- **Stop submit:** `_submit_crypto_stop` constructs the CLI args the snapshot confirmed; a submit failure returns the entry result (fail-safe), not an exception.
- **End-to-end (fixture):** the crypto strategy flows through the daily sizer path to a `submitted` crypto order with a paired resting stop.
- **Equity regression:** existing executor/sizer/lifecycle/backtest tests stay green (equity byte-identical).
- **Live smoke (spike + final):** ~$15 paper BTC entry + resting stop → reconcile rows; fractional qty confirmed in `alpaca_submissions`.

## 8. Risks & mitigations
| Risk | Mitigation |
|---|---|
| Reference strategy fails crypto thresholds → can't promote | Risk controls (abs-momentum gate + vol-target) cut drawdown; thresholds grounded by the actual backtest; if it still fails, surface + stop (no force-promote) |
| Crypto stop type/params differ from assumption | Mandatory Task-0-style spike produces real CLI evidence before stop code is written |
| Fractional qty still truncates after migration | Round-trip test + live `SELECT qty` verification after first smoke |
| Going live fires unintended equity changes | Phase C invariant unchanged; daily sizer nets crypto into existing targets; equity-regression suite |
| Crypto regime gate crashes on first tick | crypto_bars_1h.parquet already seeded (Phase B smoke); documented backfill-first ordering |
| Stop order rejected / partial | Fail-safe: entry stands, position software-managed by next cycle; logged |

## 9. Scope boundary
- **Phase D (this):** reference crypto strategy + cost/threshold/routed constants + qty migration + broker-side crypto stops + full activation (promote + 3 gates flipped + restart + smoke).
- **NOT Phase D / fast-follows (SP-3.2+):** vol-scaled crypto sizing (beyond pass-through), multi-asset crypto strategies, calibrated crypto promotion thresholds, futures, options greeks. SP-3.1 closes with Phase D — the crypto stack is fully built and live.
