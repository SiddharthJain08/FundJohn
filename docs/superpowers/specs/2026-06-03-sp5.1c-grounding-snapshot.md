## Finding 1 — Handoff emit site (`trade_handoff_builder.py`)

**File:** `src/execution/trade_handoff_builder.py`

### What the plan assumed

The plan assumed `trade_handoff_builder.py` is where `execution_signals` rows
become order/proposal dicts that flow into the sizer, and that Task 4 should
inject `option_spec` + `instrument_class` here.

### What the code actually does

`trade_handoff_builder.py` builds a **structured reporting handoff** (kind
`'structured'`) consumed by the TradeJohn confirmer and the Discord report — NOT
the sizer's order-build input.

**`load_signals` (line 79):** reads `execution_signals` with this SELECT:

```sql
SELECT strategy_id, ticker, direction, entry_price, stop_loss,
       target_1, target_2, target_3, position_size_pct,
       signal_params, regime_state
  FROM execution_signals
 WHERE signal_date = %s
 ORDER BY strategy_id, ticker
```

`signal_params` IS fetched (line 88). JSON-parsed at lines 100–104:

```python
if isinstance(d.get('signal_params'), str):
    try:
        d['signal_params'] = json.loads(d['signal_params']) if d['signal_params'] else {}
    except ValueError:
        d['signal_params'] = {}
```

**`compute_features` (line 535) + dict `out` (line 643):** the function computes
GBM-based features and returns a dict (`out`) that is the per-signal proposal.
`signal_params` is read at line 583 (`params = sig.get('signal_params') or {}`);
strategy_features from `params.get('features')` are merged at line 672. The raw
`option_spec` under `signal_params['option_spec']` is NOT carried into `out`.
`instrument_class` is NOT attached anywhere in `out`.

**This file feeds the confirmer/reporting, NOT the sharpe_cadence sizer.** The
sizer reads `execution_signals` directly via SQL (Finding 2). Carrying
`option_spec` into `trade_handoff_builder.py`'s `out` dict does NOT get it to
the executor. Task 4's insertion point may still be useful for the confirmer to
see option context, but it is not the critical carry path for execution.

**Task 4 adjustment needed:** Task 4 inserting `option_spec` into `out` at line
643 is correct for the confirmer path but does NOT connect to the sizer. The
critical carry path is `execution_signals.signal_params['option_spec']` →
`_load_active_window_signals` SELECT (Finding 2). Task 4 should note both.

## Finding 4 — Executor leg shapes (`alpaca_executor.py`)

**File:** `src/execution/alpaca_executor.py`

### `_resolve_structure_legs(spec, as_of, expiry)` — line 704

Returns `[(right, strike)] | None` where:
- Each element is a tuple `(str right, float strike)`.
- `straddle` → `[('call', k), ('put', k)]` where `k = ATM strike` (line 717).
- `strangle` → `[('call', k_call), ('put', k_put)]` from live chain greeks (lines 718–727).
- Returns `None` if any leg cannot be resolved (fail-closed).

### `_structure_net_quote(spec, legs, expiry)` — line 731

Returns `(net_ask_debit, leg_q) | None` where:
- `net_ask_debit` is a `float` (sum of per-leg asks).
- `leg_q = [(occ: str, right: str, ask: float)]` (line 743).
- Returns `None` if any leg has no quote (fail-closed).

`_dt.date.fromisoformat(r.get('expiration_date'))` (line 504) and returns

`eligible[0]` which is a `datetime.date`. Confirmed.

## Finding 5 — Instrument-class resolver (`src/strategies/instrument_class.py`)

**File:** `src/strategies/instrument_class.py`

### `instrument_class_for(strategy_id)` — line 17

```python
def instrument_class_for(strategy_id: str, manifest_path: "str | Path | None" = None) -> str:
    """Return the declared instrument_class for strategy_id, or 'equity'."""
    path = Path(manifest_path) if manifest_path else _DEFAULT_MANIFEST
    sm = LifecycleStateMachine.from_manifest(path)
    rec = sm._records.get(strategy_id)
    return rec.instrument_class if rec is not None else "equity"
```

Resolution: reads `manifest.json` → `StrategyRecord.instrument_class`. For a
strategy NOT yet in the manifest (like Task 8's reference candidate before
registration), this returns `'equity'` (the default). A strategy registered in
the manifest with `instrument_class='option'` will resolve correctly.

**For Task 8:** `S_long_straddle_delta_hedged` must either (a) be added to
`manifest.json` in `candidate` state with `instrument_class='option'` (required
for the resolver to return `'option'`), or (b) the sizer's per-ticker
instrument_class resolution must fall back to the strategy's class attribute.
Currently the sizer reads `instrument_class_for(sid)` from the manifest
(line 136 in `regime_blended_sizer_live.py`), so manifest registration is
required for routing to work.

## Surprises requiring plan adjustments

### S1 — Critical: `option_spec` cannot reach the sizer as written (blocks Tasks 5a)

The sizer's two DB loaders (`_load_active_window_signals` L306 and
`_load_approved_carried_signals` L229) only SELECT
`strategy_id, ticker, direction, signal_date, entry_price, stop_loss, target_1,
target_2`. `signal_params` (where `option_spec` lives) is NOT selected.

**Task 5a must:**
1. Add `signal_params` to both SQL SELECTs.
2. Parse `signal_params->>'option_spec'` (or full `signal_params` jsonb) per row.
3. Carry `option_spec` through `ticker_meta[tkr]` (the aggregation dict, lines 617–643).
4. Decide attribution rule: when multiple strategies contribute to the same ticker,
   which `option_spec` wins? (Likely: if any contributing strategy is `instrument_class='option'`
   take its spec; otherwise skip. Plan must document this.)
5. Include `option_spec`, `instrument_class`, `contracts` in the emitted order at line 839.

### S2 — Important: `trade_handoff_builder.py` does NOT feed the sizer

The plan's Task 4 description ("This is where Task 4 inserts `order['option_spec']`…")
is architecturally correct for the confirmer/reporting path but does NOT wire
`option_spec` to the executor. The critical carry path is:

```
engine.write_signals → execution_signals.signal_params['option_spec']
  → _load_active_window_signals (SELECT add signal_params)    [Task 5a]
  → ticker_meta[tkr]['option_spec']                           [Task 5a]
  → sizer output order['option_spec']                         [Task 5a]
  → _build_sized_payload order['option_spec']                 [Task 5b]
  → executor _route_option_order                              [Task 6/7]
```

`trade_handoff_builder.py` carries `option_spec` in `out` only for the confirmer
(informational). Task 4 should still be done for confirmer completeness, but it
is not the load-bearing path.

### S3 — Variable name correction for Task 5b

The plan uses `out_order` as the variable name for the executor order dict in
`_build_sized_payload`. The real name is **`order`** (normal path, line 160)
and **`order_oc`** (close-only path, line 97). Task 5b code must use `order`,
not `out_order`.

### S4 — Only one sizer path exists (sharpe_cadence)

The plan mentions "sharpe_cadence / consolidate / independent" order constructors.
`consolidate` and `independent` were removed 2026-05-21. Only `_sharpe_cadence_path`
exists (module docstring L5–11). Task 5a only needs to modify one SQL and one
aggregation loop.

### S5 — `strategy_id` on executor order is a composite join for multi-strategy tickers

When multiple strategies contribute to the same ticker (common in sharpe_cadence),
`strategy_id` in the executor order is `'|'.join(sorted(contributing_sids))[:120]`
(line 826 in `regime_blended_sizer.py`). For the option hedge ledger write, the
`option_strategy_id` FK value will be this composite string unless the option
strategy is the sole contributor. Task 7 should use `order.get('strategy_id')
or spec.underlying` as the fallback (the plan already documents this).

### S6 — Manifest registration NOT required for the inert proof; deferred to live-activation runbook

`instrument_class_for(sid)` reads `manifest.json` and returns `'equity'` for
unregistered strategies. However, the executor routes on
`order.get('instrument_class') == 'option'` (alpaca_executor L775), and that
flag is set by the Task 5b carry code from `option_spec` presence — NOT by
`instrument_class_for()`. The manifest resolver only feeds the SP-3 notional-sizing
path in `_build_sized_payload` (line 136), gated separately on
`OPENCLAW_INSTRUMENT_CLASS_ROUTING`.

For the inert proof (unit tests + round-trip): `instrument_class` is carried
directly from `option_spec` presence (Tasks 4/5), so manifest registration is
NOT required. Task 8's Step 5 ("do NOT promote in manifest.json") is correct.

Manifest/registry registration IS needed for a live engine cycle to emit the
signal from the reference strategy — but live activation is explicitly a deferred
runbook (SP-5.1c non-goal). The `instrument_class_for(sid) → 'equity'` for
unregistered sids is a fact to be aware of but does not block the inert proof.
