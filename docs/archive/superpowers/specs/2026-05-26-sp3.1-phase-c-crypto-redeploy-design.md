# SP-3.1 Phase C — Crypto Redeploy + Regime Gating (Design)

**Date:** 2026-05-26
**Status:** Design — approved, pending spec review
**Program:** SP-3.1 (Crypto + 24/7), Phase C of A→D
**Builds on:** Phase A (crypto execution lane) + Phase B (crypto regime detector). Both merged (`490d36f`), gates default-OFF.

---

## 1. Goal

A confirmed **crypto** regime transition triggers a **dedicated crypto-only redeploy** that adjusts crypto positions (margin-funded, 24/7) and **never touches the equity book**; and crypto strategies gate their eligibility on the **crypto** regime (not the equity regime). Gated OFF; inert until a live crypto strategy exists (Phase D).

**Explicitly NOT in Phase C:** any reference crypto strategy (Phase D), daily crypto bars in `prices.parquet` (Phase D), the `alpaca_submissions.qty INT→NUMERIC` migration (Phase D), greeks/options.

## 2. Background & the central safety constraint

- The existing redeploy (`scripts/redeploy_pipeline.py`) runs the full cycle (`signals,handoff,trade,alpaca,reconcile`) via `pipeline_orchestrator.py` for **all** strategies, gated to RTH (`_alpaca_clock_is_rth` + `OPENCLAW_REDEPLOY_EXTENDED_HOURS`).
- **The blowout failure mode (verified):** the sizer's orphan-close loop (`src/execution/regime_blended_sizer.py:_sharpe_cadence_path`, ~lines 473-479) enumerates **all** broker positions and closes any not in the current `target_usd`. A crypto redeploy carrying only crypto signals through that path would orphan-close **every equity position**. This is the SP-2-era "empty-signals-blowout" pattern ($91k flatten incident).
- Crypto trades **24/7**; the equity market is closed for most crypto-redeploy fires (overnight, weekends). Extended-hours equity fires are costly (~1% NAV/fire, ~24% unfilled — prior incident) and impossible on weekends.

**Operator decision (the design):** the crypto redeploy is a **dedicated path that never enumerates or touches equity positions**. The crypto position is **funded by the account's 4x margin headroom** — equity is never reduced. Total NAV leverage is corrected at the **next daily cycle** (the regular full-book rebalance). This makes the blowout structurally impossible: no equity-orphan-close code path exists in the crypto redeploy.

## 3. Architecture (4 components + gate)

### 3.1 Dedicated crypto redeploy — `scripts/redeploy_crypto.py` (new)
A standalone path, NOT a flag on `redeploy_pipeline.py`. On invocation it:
1. Loads **crypto strategies only** (`instrument_class_for(sid) == 'crypto'` from manifest), regime-gated on the **crypto** regime (`crypto_regime_latest.json`).
2. Generates their signals, sizes them via the existing regime-blended per-strategy weight math (§3.2), nets targets against **current crypto broker positions only** (delta = target − current, filtered to crypto tickers via the `-USD` discriminator from Phase A's `_is_crypto_ticker`).
3. Submits the resulting crypto orders via Phase A's `_route_crypto_order` (24/7, fractional, market+gtc).
- **Never enumerates equity positions** — `_load_broker_positions_usd()` output is filtered to crypto tickers before any netting/orphan logic, so equity positions are invisible to this path. There is no code branch that can close or reduce an equity position.
- **No RTH gate** (crypto is 24/7). Own cooldown namespace `redeploy:crypto:cooldown:{date}` + sentinel `redeploy:crypto:fired:{date}:{reason}` (isolated from the equity `redeploy:*` keys so the two systems never collide).
- **Min-crypto-signal gate:** if zero crypto signals are produced, the path exits without submitting — it must never flatten crypto positions on an empty signal set (the empty-signals lesson, applied to crypto).

### 3.2 Sizing relative to the prior cycle (margin-funded, no equity change)
The crypto position is sized with the same framework the daily cycle uses — `crypto_strategy_weight × NAV × crypto_regime_scale` — reading the **previous cycle's portfolio (NAV + current equity weights) as read-only context** so the crypto allocation slots into the existing risk budget at a sensible relative scale. The crypto position is **added on margin**; no equity order is ever written by this path. The next regular daily cycle re-sizes equity+crypto together and corrects total NAV leverage. (Reuses the regime-blended sizer's per-strategy weight computation, scoped to crypto strategies; the equity orphan-close/rebalance logic is not invoked.)

### 3.3 Crypto regime gating — per-strategy regime by instrument_class
`src/execution/engine.py:run_strategies` currently gates every strategy against one global `regime_state` (the equity regime). Phase C makes regime selection **per-strategy by instrument_class**: for a `crypto` strategy, eligibility (`regime_gate.is_eligible`) and the `regime` passed to `generate_signals` resolve against the **crypto** regime (`crypto_regime_latest.json`); equity/etp/option strategies keep the equity regime (byte-identical). A single added lookup (`instrument_class_for(sid)` → choose regime source); the crypto regime is loaded once per run when any crypto strategy is present.

### 3.4 The trigger — Phase B driver spawns the redeploy
`scripts/run_crypto_market_state.py` (Phase B) currently detects a confirmed transition but sets `fired_redeploy=FALSE` and never spawns. Phase C: on a confirmed transition (and gate ON), it spawns `scripts/redeploy_crypto.py` **detached** (mirroring the equity intraday spawn `_spawn_redeploy` at `run_intraday_market_state.py:458-519`), writes `fired_redeploy=TRUE` on that `crypto_regime_states` row, and respects the crypto cooldown.

### 3.5 Gate & inertness
Default-OFF gate `OPENCLAW_CRYPTO_REDEPLOY`. When OFF: the Phase B driver never spawns (transitions still logged with `fired_redeploy=FALSE`); `redeploy_crypto.py` run manually no-ops; `engine.run_strategies` per-strategy regime selection only diverges for crypto strategies (none exist until Phase D, so equity behavior is byte-identical regardless). The whole phase is inert until both this gate is ON **and** a live crypto strategy exists.

## 4. Safety invariants
- **Equity is never touched by the crypto path** — structural (no equity-position enumeration in `redeploy_crypto.py`; broker positions filtered to crypto before any netting). Verified by a test that runs the crypto redeploy with a mixed (equity+crypto) broker book and asserts zero equity orders.
- **Equity path byte-identical** — `redeploy_pipeline.py`, `regime_blended_sizer.py`'s equity path, and `engine.run_strategies` for non-crypto strategies are unchanged (the per-strategy regime lookup short-circuits to the equity regime for non-crypto).
- **No empty-signals flatten** — min-crypto-signal gate; crypto positions are never orphan-closed on an empty crypto signal set.
- **Cooldown isolation** — `redeploy:crypto:*` namespace; a crypto redeploy never blocks or is blocked by an equity redeploy.
- **Margin-bounded** — crypto adds gross exposure within the existing 4x margin; the next daily cycle corrects total leverage. (Operator note: a crypto position taken overnight runs temporarily more leveraged until the next daily cycle.)

## 6. Data flow
crypto regime tick (Phase B) → confirmed transition + gate ON → spawn `redeploy_crypto.py` (detached, crypto cooldown) → load crypto strategies (crypto-regime-gated) → signals → crypto-scoped sizing (prev-cycle weights as context, margin-funded) → net vs crypto broker positions only → `_route_crypto_order` submit → reconcile (crypto rows) → `fired_redeploy=TRUE`. Equity book untouched until the next daily cycle.

## 7. Testing
- **Equity-untouched (the load-bearing test):** crypto redeploy with a mocked mixed broker book (SPY + BTC-USD) → asserts only crypto orders emitted, zero equity orders, equity positions enumerated nowhere.
- **Min-signal gate:** zero crypto signals → no orders (no flatten).
- **Crypto-regime gating:** a crypto strategy's eligibility resolves against `crypto_regime_latest.json`, an equity strategy against the equity regime (engine `run_strategies` unit test with both).
- **Cooldown namespace:** crypto cooldown key distinct from equity; no cross-block.
- **Spawn:** Phase B driver spawns `redeploy_crypto.py` on confirmed transition when gated ON; `fired_redeploy` set.
- **Equity regression:** existing redeploy/sizer/engine tests stay green (equity path byte-identical).
- **Synthetic crypto strategy fixture** (no live crypto strategy until Phase D) drives the end-to-end test.

## 8. Scope boundary
- **Phase C (this):** the redeploy machinery + regime gating + trigger, gated, equity-safe, tested with a fixture.
- **Phase D:** mints the first live crypto strategy (candidate), daily crypto bars into `prices.parquet`, crypto `INSTRUMENT_COST_BPS`/`PROMOTION_THRESHOLDS`/`ROUTED_INSTRUMENT_CLASSES`, broker-side crypto stops, and the **`alpaca_submissions.qty INT→NUMERIC`** migration (fractional crypto qty currently rounds to 0 in the audit row). Until D, Phase C is inert (no crypto strategy → no crypto signals → no crypto orders).

## 9. Risks & mitigations
| Risk | Mitigation |
|---|---|
| Crypto redeploy orphan-closes equity | Dedicated path never enumerates equity; broker filtered to crypto; load-bearing equity-untouched test |
| Empty crypto signals flatten crypto | Min-crypto-signal gate (exit without submitting) |
| Overnight over-leverage | Bounded by 4x margin; next daily cycle corrects; operator-visible |
| Cooldown collision with equity redeploy | `redeploy:crypto:*` namespace |
| Per-strategy regime change leaks into equity | Lookup short-circuits to equity regime for non-crypto; equity-regression tests |
| `crypto_regime_latest.json` missing (gate just enabled) | Crypto gating fails-open to "eligible" or skips crypto strategies cleanly; documented backfill-first ordering |
